1. Projeto e objetivo final

    ERP legado VB6 + MySQL 4.1 (PDV, mesas, financeiro, caixa, estoque).

    Serviço PHP intermediário entre apps e banco.

    Facilit App (React Native/Expo) — app mobile de mesas, pronto.

    Facilit (React → Electron) — PDV desktop novo, em construção, foco atual.

    ERP 2.0 — futuro, migração do VB6.

    Objetivo atual: emitir NFC-e no fechamento da venda via componente TecnoSpeed v6.0 (DLL/OCX via COM). Depois: TEF (débito, crédito, PIX).

5. Decisões de arquitetura/design já tomadas

    NFC-e emitida após fechamento da venda. vendas.status: 0=aberta, 1=fechada, 2=cancelada.

    vendas.vendedor = código do funcionário (não do usuário). funcionarios.USER é palavra reservada (usar backticks).

    Integração escolhida: PHP no Windows chama COM (new COM("NFCeX.spdNFCeX")), com php_com_dotnet habilitado.

    Venda NÃO é desfeita se NFC-e falhar — só loga pendência.

    Componente TecnoSpeed não é thread-safe — precisará de fila/lock depois.

    origem (FACILIT / FACILIT_APP) deve ser gravada em vendas, recebido.origem_recebimento, caixa_movimento.origem.

    Modelo 65, versão 4.00, série 1, ambiente padrão homologação.

8. Pegadinhas ou decisões não óbvias

    MesaDetalhesModal.jsx (original) tem handleFinalizar só com alert — não é o fechamento real. O correto é MesaDetalhesModal2.jsx + FinalizarVendaModal.jsx.

    SuccessModal é "componente burro" — nunca precisa saber de NFC-e; o pai monta detalhes[].

    pagamentoService.js é o arquivo certo (não mesaService.js).

    finalizarEEmitir só loga falha da NFC-e; venda permanece fechada.

    Correções já aplicadas em NfceFiscal.php: ide_indfinal=1, isReformaAtiva com IS NOT NULL, distribuição proporcional do desconto do cabeçalho, vProd prioriza total_bruto, guard contra status ≥ 100.

    Divergência item × cabeçalho causa rejeição SEFAZ 531/532.

    funcionarios.USER é palavra reservada SQL.

    vendas.vendedor = funcionarios.codigo, não usuarios.codigo.
