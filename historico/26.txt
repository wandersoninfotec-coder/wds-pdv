5. BUG ATUAL — XML de cancelamento não salva
Sintoma

Após cancelar com sucesso (cStat=135, status_nfce=6), os campos tab_nfce.xml_cancelado e tab_nfce.xml_cancelado_ret continuam nulos.
Onde investigar (no NfceTransmissor::cancelar())

O bloco que faz o UPDATE já existe (foi aplicado), mas algo falha silenciosamente. Possíveis causas:

    rowCount()=0 — a WHERE emp_codigo=:emp AND numero_nfce=:num não bate

    Colunas xml_cancelado / xml_cancelado_ret não existem em tab_nfce (ou nome diferente)

    montarProcEventoCancelamento() retornou vazio ou com erro, mas o bindValue não falhou

Ação imediata

    Confirma colunas:
    sql

    SHOW COLUMNS FROM tab_nfce LIKE 'xml_cancelado%';

    Adiciona log com rowCount no bloco do UPDATE do cancelar():
    php

    $sql->execute();
    $this->log("UPDATE xml_cancelado | rowCount=" . $sql->rowCount());

    Loga o tamanho do XML gerado antes do bind:
    php

    $this->log("XML cancelado gerado: " . strlen($xmlCancelado) . " bytes");
    $this->log("XML ret gerado: " . strlen($xmlCanceladoRet) . " bytes");

    Testa o UPDATE manual no MySQL com o número:
    sql

    UPDATE tab_nfce SET xml_cancelado = 'TESTE' WHERE emp_codigo = 1 AND numero_nfce = <N>;

Comparação com VB6 (referência)
vb

UPDATE tab_nfce SET
    xml_cancelado_ret='...',
    xml_cancelado='...'
WHERE emp_codigo=... AND numero_nfce=...

O VB6 faz em um único UPDATE. O PHP faz em 2 UPDATEs separados (status + XMLs) — isso está OK, o problema é que o segundo não está gravando.
